- (decision) Architecture hexagonale retenue pour séparer le cœur métier des adaptateurs et empêcher les choix d'infrastructure de contaminer les cas d'utilisation.
- (decision) La persistance est un port secondaire orienté domaine ; aucun cas d'utilisation ne dépend directement d'un SQL, d'un ORM ou d'un document NoSQL.
- (decision) Les tests unitaires utilisent un adaptateur de persistance en mémoire ; le développement local utilise un adaptateur SQLite.
- (question) Le moteur de persistance des environnements serveur (test et production) reste à choisir ultérieurement, PostgreSQL étant une option candidate et NoSQL restant possible après étude des besoins.
- (direction) Cible de déploiement serveur : Nginx en frontal, fichiers statiques du frontend servis par Nginx, backend dans un conteneur Docker accessible en réseau privé, base de données dans un conteneur séparé accessible uniquement par le backend.
- (constraint) Le conteneur de base de données ne doit pas être exposé directement au réseau public ; les données persistantes doivent reposer sur un volume et une stratégie de sauvegarde définie avant la production.
- (decision) Pour la V1, le frontend compilé et le backend sont livrés dans un conteneur applicatif unique ; Nginx termine HTTPS et relaie vers ce conteneur ; la base de données reste dans un conteneur séparé sur un réseau privé.
- (decision) Pour la V1, l'application est exposée publiquement derrière HTTPS sans authentification applicative ; ce choix est un risque accepté et devra être réévalué avant toute utilisation de données sensibles ou multi-utilisateur.
- (decision) Correction de cadrage : Node.js est le runtime backend visé ; Nuxt.js n'est pas retenu ni requis. Fastify reste un framework HTTP candidat exécuté sur Node.js ; le framework frontend reste à choisir séparément.
- (direction) Pour le frontend, Vue 3 + TypeScript + Vite est la recommandation de travail : continuité avec l'expérience Vue 2, outillage TypeScript officiel et complexité adaptée à une V1 ; React reste l'alternative si la familiarité ou l'écosystème priment, Angular n'est pas privilégié pour cette V1.
- (decision) Le frontend V1 utilise Vue 3 avec TypeScript ; le backend expose l'API avec Fastify sur Node.js ; le domaine et les ports restent indépendants de Vue, Fastify et des détails d'infrastructure.
- (decision) Le frontend Vue communique avec le backend Fastify au moyen d'une API REST JSON ; les routes HTTP restent des adaptateurs et délèguent aux cas d'utilisation du cœur.
- (decision) Les valeurs financières utilisent un décimal exact, jamais un flottant ; la V1 supporte jusqu'à huit décimales pour montants, prix, quantités et taux de change, avec devise et valeur sérialisées explicitement en JSON sans perte de précision.
- (decision) En V1, les transactions et cotations métier utilisent une date calendaire sans heure ; les horodatages UTC sont conservés pour les événements techniques et la récupération des données. Les transactions intrajournalières restent une évolution future.
- (decision) Lorsqu'une transaction est enregistrée dans une devise différente de la devise par défaut, la transaction conserve le montant et la devise d'origine, le montant converti dans la devise par défaut, le taux appliqué et la date de conversion.
- (decision) L'enregistrement d'un achat et le débit des liquidités sont atomiques ; les transactions et mouvements de liquidité constituent la source de vérité, tandis que la position est une vue dérivée reconstruisible.
- (decision) Les transactions constituent l'unique source de vérité ; le solde de liquidité est recalculé à partir des effets des transactions et n'est pas persisté comme état autonome. Les types de transaction prévus par le modèle comprennent apport, retrait et achat, sous réserve du périmètre fonctionnel de chaque version.
- (question) Décider si le retrait de liquidité est exposé dans la V1 ou seulement réservé au modèle futur ; le type de transaction peut être prévu sans livrer son cas d'utilisation.
- (decision) Le périmètre fonctionnel V1 expose les apports de liquidité et les achats uniquement ; les retraits de liquidité et les ventes sont réservés aux versions futures, tout en restant des types extensibles du registre de transactions.
- (event) Architecture spine finalisée après lint et revues rubric, fraîcheur technologique et adversariale ; les points différés sont listés pour le scaffold, le spike marché et le déploiement.
